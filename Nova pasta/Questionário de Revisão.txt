Questionário de Revisão — UC10: Gerenciamento de Configuração e Versionamento de Softwares

1. Diferença entre reset e revert: 
Explique a diferença fundamental entre o funcionamento dos comandos git reset e git revert ao desfazer alterações em um projeto, detalhando o que ocorre com o histórico de commits em cada caso.
Resposta: - O "git reset" desfaz as alterações movendo o estado do histórico para o commit anterior. Já o "git reverte" desfaz as modificações enviados por um commit sem apagar isso do histórico, gerando um novo ponto no branch

2. Significado de HEAD~1: No contexto do comando git reset HEAD~1, o que a expressão HEAD~1 representa e qual é o resultado prático dessa operação na branch atual?
Resposta: - Head~1 é o commit diretamente anterior ao commit atual da branch ou seja, o comando "git reset HEAD~1" vai desfazer o ultimo commit utilizado.
 

3. Uso do --amend: Em quais situações um desenvolvedor deve utilizar a opção --amend no comando git commit? Cite pelo menos dois exemplos de modificações que podem ser feitas com esse recurso.
Resposta: - esse comando é usado para modificar o ultimo commit realizado na branch atual. Pode ser usado para corrigir pequenos erros de código que foram percebidos após enviar o commit, por exemplo, 
ou até para corrigir erros de digitação percebidos porsteriormente... ele  serve para quando as modificações são pequenas e não vale a pena fazer um novo commit.


4. Estrutura do Gitflow: Descreva o objetivo do modelo de colaboração Gitflow e explique a função de cada uma de suas cinco branches principais (Main, Develop, Feature, Release e Hotfix).
Resposta: - Gitflow, por obvio, é um modelo de trabalho workflow para git, tem por objetivo prover uma estrutura organizada de ramificação (branching) para ser utilizada no desenvolvimento d softweres. 
Permitindo equipes isoladas trabalharem num mesmo projeto de maneira coesa. : "Branch Main": Linha Oficial, estável, permanente, principal... "Branch Develop" também é permanente mas é um ambiente de integração do projeto, 
é criada a partir da Main e serve para agrupar todas as funcionalidades... "Branch Feature": Temporaria, ramificada a partir da Develop para desenvolver novas funcionalidades. "Branch Release" temporária usada para preparar 
o lançamento de uma nova versão de softwere... "Branch Hotfix" temporária usada para resolver bugs críticos eemergenciais.


5. Vantagens do Gitflow no ciclo de vida: De que maneira a criação e a fusão de ramificações no modelo Gitflow ajudam a evitar conflitos durante o desenvolvimento de um software?
Resposta: - Graças as branch o modelo inteiro pode ser dividido, separado, testado e unificado, parte por parte e mantendo da Branch Main apenas o que já foi testado e esta perfeito... 


6. Funcionamento do Trunk-Based Development: Como funciona o modelo Trunk-Based Development e qual é a principal justificativa para adotá-lo em um projeto?
Resposta: - Modelo que usa uma única Branch onde os devs vão completando o código com commits contínuos e curtos se completando aos poucos. O principal motivo para se usar esse tipod e desenvolvimento é eliminar 
o "merge hell" (conflitos complexos de integração) e acelerar a entrega contínua (CI/CD), mantendo o software sempre em um estado pronto para implantação.


7. Boas práticas no Trunk-Based Development: Como todas as alterações no Trunk-Based Development são feitas diretamente na branch principal, quais práticas são consideradas fundamentais para evitar conflitos no projeto?
Resposta: - Para melhor organizar, manter o fluidez e evitar erros de continuidade é interessante que os desenvolvedores usem commits pequenos e frequentes;  atualização constante da cópia local,  Antes de enviar qualquer alteração, baixe as novidades do trunk usando git pull --rebase. Isso coloca seus commits no topo do histórico mais recente, permitindo resolver microconflitos localmente antes mesmo de integrá-los; revisão de código ageis, evitando demora nas resoluções das Pull Requests


8. Problemas do armazenamento centralizado sem versionamento: Antes do surgimento das ferramentas de controle de versão, múltiplos usuários acessavam um mesmo arquivo em um servidor central. Quais eram os dois principais problemas que ocorriam quando duas ou mais pessoas tentavam editar esse arquivo simultaneamente?
Resposta: - Sobrescrita de alterações: Quando dois usuários abriam o arquivo ao mesmo tempo, ambos carregavam uma cópia local na memória de seus computadores. O usuário que salvasse o arquivo por último apagava silenciosamente todas as alterações feitas pelo primeiro / Conflitos de versão e duplicação: Para tentar evitar a perda de código ou texto, as equipes criavam cópias manuais renomeando os arquivos. Isso gerava múltiplas versões espalhadas pelo servidor, dificultando descobrir o atual arquivo correto.


9. Sistemas centralizados vs. distribuídos: Qual era a principal vulnerabilidade das ferramentas antigas de controle de versão centralizado (como CVS e Subversion) em caso de falha no servidor, e como os Sistemas de Gerenciamento de Versões Distribuídos (SGVD), como o Git, resolvem esse problema?
Resposta: - O problema principal era a dependência de um servidor único para todo o trabalho, gerando perda de históricos das versões, dificultando o trabalho de múltiplos devs, e facilitando a corrupção e extravio de dados. 

10. Popularidade do Git e papel do GitHub: Além de ser um sistema distribuído e performático, qual é o papel da plataforma GitHub na ampla adoção do Git pela comunidade de desenvolvimento e pelo ecossistema open-source?
