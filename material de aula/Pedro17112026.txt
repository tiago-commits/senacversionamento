Questionário de Revisão — UC10: Gerenciamento de Configuração e Versionamento de Softwares

1. Diferença entre reset e revert: Explique a diferença fundamental entre o funcionamento dos comandos git reset e git revert ao desfazer alterações em um projeto, detalhando o que ocorre com o histórico de commits em cada caso.

O git reset apaga o commit atual assim desfazendo as alterações feitas nele ao ir para o commit anterior, enquanto o git revert cria um novo commit e nele ele desfaz as alterações feitas no commit anterior


2. Significado de HEAD~1: No contexto do comando git reset HEAD~1, o que a expressão HEAD~1 representa e qual é o resultado prático dessa operação na branch atual?

HEAD~1 é o commit anterior ao atual, e ao realizar o comando git reset HEAD~1, o commit realizado é desfeito pelo git.  As alterações feitas nesse commit não são perdidas, mas voltam para o diretório de trabalho como arquivos modificados e não preparados para commit


3. Uso do --amend: Em quais situações um desenvolvedor deve utilizar a opção --amend no comando git commit? Cite pelo menos dois exemplos de modificações que podem ser feitas com esse recurso.

O desenvolvedor deve utiliza-lo quando precisar fazer uma alteração no arquivo sem criar um commit. Por exemplo: quando precisar corrigir a mensagem do commit por erro de digitação ou falta de clareza, ou adicionar arquivos esquecidos.


4. Estrutura do Gitflow: Descreva o objetivo do modelo de colaboração Gitflow e explique a função de cada uma de suas cinco branches principais: Main, Develop, Feature, Release e Hotfix.

O Gitflow é um modelo de fluxo de trabalho que organiza o desenvolvimento de software por meio de regras rígidas para criação e fusão de branches, sendo muito útil para projetos com ciclos de lançamento programados.

Main ou Master: Armazena apenas o código oficial de produção, sempre estável e pronto para uso final.

Develop: Funciona como a branch de integração, reunindo todas as funcionalidades já concluídas que farão parte da próxima versão.

Feature: Criada a partir da Develop para desenvolver uma nova funcionalidade de forma isolada, retornando para a Develop ao ser finalizada.

Release: Criada a partir da Develop para preparar uma nova versão de lançamento, permitindo apenas testes finais e correções de bugs menores antes de ir para a Main e voltar para a Develop.

Hotfix: Criada diretamente a partir da Main para corrigir falhas críticas em produção de forma urgente, sendo depois mesclada tanto na Main quanto na Develop.


5. Vantagens do Gitflow no ciclo de vida: De que maneira a criação e a fusão de ramificações no modelo Gitflow ajudam a evitar conflitos durante o desenvolvimento de um software?

O Gitflow evita conflitos ao isolar os diferentes contextos de trabalho em ramificações específicas.


6. Funcionamento do Trunk-Based Development: Como funciona o modelo Trunk-Based Development e qual é a principal justificativa para adotá-lo em um projeto?

No Trunk-Based Development (TBD), todos os desenvolvedores integram suas alterações diretamente em uma única branch principal (chamada de trunk ou main), ou usam branches de vida muito curta, poucas horas ou no máximo um dia. Tem como justificativa eliminar o chamado "merge hell", inferno de mesclagem, causado por branches de longa duração, acelerando a entrega contínua (CI/CD) e permitindo que a equipe detecte problemas de integração quase em tempo real.


7. Boas práticas no Trunk-Based Development: Como todas as alterações no Trunk-Based Development são feitas diretamente na branch principal, quais práticas são consideradas fundamentais para evitar conflitos no projeto?

Temos por exemplo: Commits pequenos e frequentes, pois ao enviar pequenas partes de código várias vezes ao dia facilita a revisão e reduz a chance de conflitos complexos, testes automatizados e Integração Contínua (CI) e Feature Flags 


8. Problemas do armazenamento centralizado sem versionamento: Antes do surgimento das ferramentas de controle de versão, múltiplos usuários acessavam um mesmo arquivo em um servidor central. Quais eram os dois principais problemas que ocorriam quando duas ou mais pessoas tentavam editar esse arquivo simultaneamente?

Ocorriam sobrescrita de alterações em que se dois usuários abrissem o mesmo arquivo ao mesmo tempo, quem salvasse por último apagava acidentalmente todo o trabalho feito pelo colega, e a perda de histórico e rastreabilidade pois não havia registro de quem alterou o quê, quando a mudança ocorreu ou como restaurar uma versão anterior caso um erro fosse introduzido.

9. Sistemas centralizados vs. distribuídos: Qual era a principal vulnerabilidade das ferramentas antigas de controle de versão centralizado (como CVS e Subversion) em caso de falha no servidor, e como os Sistemas de Gerenciamento de Versões Distribuídos (SGVD), como o Git, resolvem esse problema?

A principal vulnerabilidade dos sistemas centralizados, como CVS e SVN, era o ponto único de falha. O problema nos centralizados era que como todo o histórico de versões ficava armazenado exclusivamente no servidor central, se o servidor caísse, os desenvolvedores não podiam salvar versões, fazer commits. Se o disco do servidor corrompesse sem backup, todo o histórico do projeto era perdido. A Solução nos distribuídos, SGVD, é que Ferramentas como o Git fazem com que cada desenvolvedor tenha um clone completo do repositório em sua própria máquina, incluindo todo o histórico. Assim, é possível trabalhar offline e restaurar o projeto inteiro a partir da máquina de qualquer membro da equipe caso o servidor saia do ar.


10. Popularidade do Git e papel do GitHub: Além de ser um sistema distribuído e performático, qual é o papel da plataforma GitHub na ampla adoção do Git pela comunidade de desenvolvimento e pelo ecossistema open-source?

O GitHub foi fundamental para a popularização do Git ao transformar uma ferramenta de linha de comando técnica em uma plataforma visual, colaborativa e social. Ele reduziu a barreira de entrada para novos desenvolvedores e centralizou o ecossistema open-source em um só lugar.
